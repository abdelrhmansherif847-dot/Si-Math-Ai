⚠️ This panel cannot see every failure. It detects failures by reading question_records. When ai-tutor returns HTTP 5xx — an unhandled error, a bad deploy, a crash before the insert — no row is written, so the request is invisible here no matter what the student saw. A quiet panel therefore means "nothing failed in a way that reached the database", not "nothing failed". Confirmed case: two POST 500 responses on 2026-07-29 left zero rows behind.

Where to look instead, right now: Supabase Dashboard → Edge Functions → ai-tutor → Logs, and filter on status 500.

To close the gap: ai-tutor's top-level error handler must insert a question_records row (or write to a dedicated failure table) before returning 5xx, recording the status and error. That is an Edge Function change — it cannot be fixed from this dashboard, which has read-only access to the database and no access to the function log stream.

Requirements to enable the remaining signals
  1. ✅ Done (2026-07-30) — per-call telemetry. public.ai_model_calls is now read through two owner-gated SECURITY DEFINER RPCs, giving measured call counts, per-model attribution, per-stage latency, and a provider-failure signal independent of question_records. The table itself stays service-role with no policy; the RPCs return a fixed operational column set and are refused with HTTP 403 below role owner.
  2. Failures that never reach the database. When ai-tutor returns 5xx before its insert, nothing is written to question_records or ai_model_calls, so no read path can surface it — the RPCs above do not close this gap. Needs: an ai-tutor change so the top-level error handler persists the failure before returning. No new credentials. This is now the highest-value remaining unlock.
  3. Rate-limit headroom. ai-tutor must read the x-ratelimit-remaining-requests, x-ratelimit-remaining-tokens and x-ratelimit-reset-* response headers off every OpenAI response and persist them. Needs: an ai-tutor code change. No new credentials.
  4. Model availability / deprecation checks. Requires GET /v1/models, which needs a standard OpenAI API key. It cannot be called from this page — that would expose the key in the browser. Needs: a small server-side Edge Function proxy that holds the key and returns only the model list.
  5. Organization-level usage & rate-limit configuration. Requires an OpenAI Admin API key (sk-admin-…) plus the Organization ID (org-…) and Project ID (proj_…), called server-side against the organization endpoints. Needs: the admin key stored as an Edge Function secret, plus a scheduled job to snapshot results.
  6. Account balance / credit remaining. OpenAI publishes no API for this. The only authoritative early warning is a usage limit and billing alert configured in the OpenAI dashboard. Nothing this dashboard can add will change that — no balance figure will ever be shown here.
Spend, burn rate, and cost projections are out of scope for AI Monitor by design — they belong to AI Economics in the Owner Dashboard.
